# 00—09 模块职责边界

本文是新版流水线的模块边界基准。模块的实现、提示词和数据契约发生冲突时，先按
本文判断职责归属，再修改代码；不得因为某一步暂时方便而把下游职责塞回上游。

## 1. 总边界矩阵

| 模块 | 主要输入 | 唯一职责 | 正式输出 | 明确禁止 |
|---|---|---|---|---|
| 00 语料导入 | 原始小说文件 | 编码识别、切章、自然段定位、来源哈希 | `ChapterDocument` | 理解剧情、改写原文、调用作者 Skill |
| 01 剧情压缩 | `ChapterDocument` 的全章分块导航与语义块 | 提取章首/章末边界帧与中等粒度局部剧情段，并合并章纲 | `ChapterSynopsisBundle` | 原子事实、实体关系、逐段动作账本、卷纲、文风 |
| 02 分层大纲 | 已接受的章节梗概 | 跨章聚合故事弧、卷和全书的主要事件与长程变化 | `HierarchicalOutlineBundle` | 读取整章原文、补抽事实、实体合并、语言风格 |
| 03 按需事实补全 | 分层大纲提出的事实需求 + 原文检索窗口 | 只回答支撑大纲与后续生成所需的事实问题 | `FactHydrationBundle` | 无差别事实覆盖、全局实体合并、编造无证据答案 |
| 04 叙事图谱 | 已验证事实、大纲和旧图谱状态 | 实体合并、关系、因果、时空、状态、线索生命周期及补丁提交 | `narrative_graph.json` 与校验报告 | 文风蒸馏、正文生成、从原文自由补事实 |
| 05 结构模板 | 多作品大纲、图谱和结构观测 | 蒸馏宏观、事件、场景、人物、节奏和悬念模板 | 模板库 | 提取语言风格、保存原作专名剧情、单样本直接升级作者规律 |
| 06 文风蒸馏 | 带场景标签的原文样本与对照语料 | 量化并归纳作者的语言、视角、叙述距离、节奏和信息释放策略 | 作者风格档案 | 复制长原文、决定新故事剧情、把题材词当作者风格 |
| 07 Skill 编译 | 已验证模板、风格档案和使用约束 | 编译可安装、可执行、可验证的小说作者 Skill 与提示词程序 | `{author_id}_skill/` | 继续抽取原文、携带可还原原作的剧情库、直接生成章节 |
| 08 受控生成 | 新故事规划、相关图谱子图、作者 Skill、上一段收束 | 分层计划、分段写作、正文校验和图谱补丁事务 | 小说正文、验证记录、已提交补丁 | 读取未来原文、把整章原文喂给生成器、校验失败后强行提交 |
| 09 评测归因 | 生成物、计划、图谱、Skill；重建模式下可隔离读取原文 | 分别评价剧情、连续性、可读性和文风，并归因到具体模块 | 评测与误差归因报告 | 向生成器泄漏答案、静默改产物、降低标准掩盖失败 |

## 2. 原文访问权限

| 模块 | 是否可读原文 | 读取方式 |
|---|---:|---|
| 00 | 是 | 完整读取，仅做确定性切分和定位 |
| 01 | 是 | 导航请求通读整章但只划分范围；局部请求只以一个语义块为输出依据并读取极少邻接上下文 |
| 02 | 否 | 只读第一模块正式章纲 |
| 03 | 是 | 由 `FactRequirement` 定向检索相关窗口 |
| 04 | 原则上否 | 只读已验证事实及其证据定位；必要复核走第三模块 |
| 05 | 原则上否 | 只读大纲、图谱和结构观测 |
| 06 | 是 | 读取按场景抽样且完成样本隔离的原文片段 |
| 07 | 否 | 只读聚合后的作者知识 |
| 08 | 否 | 重建测试也禁止读取待生成章节原文和未来答案 |
| 09 | 条件允许 | 只在隔离评测端读取留出原文，不回传给生成端 |

## 3. 各模块详细边界

### 00：语料导入

- 负责：识别文本编码、切分作品和章节、保留标题与原始次序、生成稳定字符范围和哈希。
- 输出必须保持正文不可变；同一来源重复导入应得到相同稳定 ID。
- 不负责判断某段是不是伏笔、事件、场景或人物描写。
- 验收：章节无重叠丢失、字符范围可回切原文、来源哈希一致。

### 01：中等粒度剧情压缩

- 负责：先把整章划分为连续、无遗漏、无重叠的语义块，再按实际推进提取局部剧情段，并直接形成允许多句的完整章节梗概。
- 首分块额外生成一句正文第一帧状态，末分块额外生成一句正文最后一帧状态；它们是
  章纲边界，不是人物状态账本。章级模型只能引用，不能改写这两个边界句。
- 只保留目标、真实阻力、决定、主要行动、关键认知、局势和阶段结果的变化。
- 段落 ID 只是回查依据；`reviewed_source_unit_ids` 只是确定性语义分块覆盖元数据。
- 章级压缩只读局部梗概，不回读原文；章节梗概直接引用全部局部梗概，不在第一模块内增加节点分组层。
- 不负责：逐段用途、动作/对话清单、人物卡、事实、实体、关系、标准化时空、知识图谱、
  跨章事件弧、伏笔生命周期和作者文风。
- 验收：主要走向忠实、没有确定性升级、主要推进没有遗漏；详略与拆分方式不作为语义否决项。
- 边界验收：第一帧不得倒退成首个事件的逻辑前提，最后一帧不得停留在章中旧状态；
  非首/末语义分块不得产生章首/章末状态。

### 02：分层大纲

- 负责：把相邻章节的局部梗概和章节梗概聚合成事件链和故事弧，整本路线继续聚合为卷和全书。
- 在这一层描述长程目标、压力、因果、转折、人物发展和未决问题，但它们仍是大纲判断，
  不是原子事实。
- 短样本路线最高到局部故事弧；整本路线最高到卷或全书。两条路线复用同一聚合器。
- 不负责回原文证明人物具体动作、关系或状态，不得用常识补全样本之外的未来走向。
- 验收：子节点完整覆盖、顺序与因果可解释、聚合层没有重复事件和越界预测。

### 03：按需事实补全

- 负责：大纲节点先提出“后续必须知道什么”，再回到原文回答这些具体问题。
- 允许提取人物称呼、事件前提与结果、关系、状态、时空和线索证据，但每项必须关联
  `FactRequirement`、大纲节点和原文范围。
- 不负责追求全书每句事实覆盖，也不负责跨章统一实体 ID 或直接维护图谱。
- 验收：事实有明确用途和证据；无法回答时保持未回答，不用模型猜测填空。

### 04：叙事图谱

- 负责：把局部称呼合并为全局实体，建立人物关系、事件因果、时间偏序、空间迁移、
  人物状态和知识状态，并维护线索从出现到回应或失效的生命周期。
- “伏笔”必须同时具有前文设置和后文回应证据；只有设置没有回应的是开放线索或未填坑，
  不能标为已验证伏笔。
- 每章生成后的图谱修改先是 `proposed` 补丁；只有正文支持、状态和因果均通过才可 `committed`。
- 不负责语言风格和小说正文。
- 验收：实体合并可解释、状态无硬冲突、因果有方向、未通过补丁不污染正式图谱。

### 05：结构模板蒸馏

- 负责：从多章、多事件和多作品中归纳“作者如何组织故事”的可复用模板，包括宏观、
  事件、场景、人物、节奏和悬念模板。
- 每个候选先属于作品；跨章节、跨作品重复且通过反例和同题材对照后才能升级为作者模板。
- 不负责句式、用词、修辞等语言风格，不得把角色名、功法名和原作事件序列放入作者模板。
- 验收：模板有适用条件、步骤、叙事作用、支持样本、反例、稳定度和区分度。

### 06：文风蒸馏

- 负责：按场景类型量化叙述视角、叙述距离、句段长度、对话/动作/心理/环境比例、
  信息释放、节奏、修辞、情绪推进和负面倾向。
- 可以读取原文样本，但输出必须是聚合规律、范围和短证据定位，不能成为长原文仓库。
- 作品内特征先与同题材对照，排除题材词、世界设定和单书角色口癖。
- 不负责确定剧情发生什么，也不生成正文。
- 验收：跨作品稳定、场景条件明确、具有反例和可执行的正负约束。

### 07：作者 Skill 编译

- 负责：把已验证结构模板和风格档案编译成目录、`SKILL.md`、提示词程序、运行参数、
  质量检查和版本清单。目录名由用户输入的作者代号决定。
- Skill 只描述“怎么构思、怎么组织、怎么写和怎么自检”，不携带可顺序还原原作的事实全集。
- 不负责继续分析原文或承担运行时故事记忆。
- 验收：可安装、可调用、输入输出明确；去除专名后仍体现作者级写法；盲测优于通用基线。

### 08：受控长文生成

- 负责：先根据卷级/事件级/章节级约束形成章节计划，再按场景和段落生成 4000—8000 字正文。
- 每段只读取当前写作任务相关的图谱子图、宏观约束、前文必要收束和作者 Skill；长程因果由
  卷/事件/章节大纲承载，短程连贯由场景状态和上一段收束承载。
- 每章结束提出图谱补丁，正文、人物状态和事件因果全部通过后才允许提交并进入下一章。
- 不负责读取原作未来章节作为提示，也不能在校验失败时回退成粗糙摘要或降低标准。
- 验收：正文完整、跨段连贯、跨章状态一致、计划兑现、补丁事务正确。

### 09：评测与错误归因

- 负责：分别评价核心剧情覆盖与顺序、因果、人物选择、状态连续、章节完整度、可读性、
  文风执行和作者辨识度。
- 报告必须区分：第一模块梗概错误、第二模块长程大纲错误、第三模块事实不足、第四模块图谱
  错误、检索错误、生成执行错误、模型能力不足和校验器误判。
- 重建评测可以在隔离端读取原文，但原文和答案不得进入生成提示词或作者 Skill。
- 不负责直接修改正式图谱、Skill 或正文；修复必须回到责任模块产生新版本。
- 验收：指标有独立测试集和基线，问题可定位到模块，不能以降低阈值替代修复。

## 4. 合法数据流

```text
00 ──→ 01 ──→ 02 ──→ 03 ──→ 04
│      │       │              │
│      │       └────→ 05 ←────┘
│      └────────────→ 09
├──────────────→ 06 ──┐
│                     ├──→ 07 ──→ 08 ──→ 09
└──────────────→ 03/09┘             ↑
                         新故事规划 + 相关图谱子图
```

跨模块只能读取对方的正式版本化产物，不得导入其他业务模块的内部提示词、解析器、
私有检查点或失败产物。

## 5. 边界变更规则

- 一个字段只能有一个责任模块；下游发现缺失时，必须向上游提出需求，不能私自回读原文补写。
- 模块可以拒绝不合格输入，但不能在输出中顺便完成后续模块职责。
- 新字段进入公共契约前，必须同时写明生产者、消费者、证据来源、验收者和禁止用途。
- 模块内部可使用中间态减轻模型负担；中间态不是跨模块接口，下游不得依赖。
- 所有调用模型的模块必须把提示词放在本模块的 `prompts/templates/` 目录，并按
  [PROMPT_CONVENTIONS.md](PROMPT_CONVENTIONS.md) 分离模板、动态数据构建和版本指纹。
- 本文优先于旧流程说明；修改模块边界时必须同步规格、数据契约、流水线文档与模块 README。
