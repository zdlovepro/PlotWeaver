# 软件需求规格（SRS）

## 1. 项目目标

系统从同一小说作者的多部作品中恢复故事组织方式、人物决策逻辑、长篇节奏和语言表达规律，将经过验证的规律编译为可复用的小说作者 Skill，并通过受控重建和新题材写作验证其有效性。

## 2. 关键研究内容

1. 长篇小说的分层梗概提取：先形成局部剧情段和章节梗概，再逐层合并为故事弧、卷和全书结构。
2. 必要事实与叙事图谱：围绕事件前提、结果和持续状态建立人物关系、因果、时空和伏笔生命周期。
3. 作者写法蒸馏：从多部作品中区分通用写法、作品偏移和作者稳定模板，并量化场景化文风。
4. Skill 生成与质量闭环：生成可执行提示词工程，用重建生成、结构评分、连续性校验和文风评测持续改进。

## 3. 功能需求

00—09 阶段的详细输入、输出、原文访问权限与禁止事项见
[MODULE_BOUNDARIES.md](MODULE_BOUNDARIES.md)。功能实现不得跨越该边界以规避质量问题。

### FR-01：语料管理

系统应从 `input/` 接收任务，从 `novels/` 选择作者作品；保留来源哈希、章节编号、标题、字符位置和编码信息。语料、密钥和运行产物不得上传公共仓库。

### FR-02：安全切分

系统应按章节和自然段切分长文本。模型请求必须有明确长度上限，不得把整本小说一次性交给模型，也不得依赖截断后的不完整 JSON。

### FR-03：局部与章节梗概

第一模块应把受限原文窗口压缩为中等粒度局部剧情段，再仅使用这些局部结果形成
允许多句的完整章节梗概。首、末窗口应各提供一个不可由章级模型改写的正文边界句，
以防章首状态倒退或章末状态滞留。第一模块不得增加章级节点或章节阶段，也不得
逐段登记动作、对话和用途，也不得输出事实、命题、实体或知识图谱。

### FR-04：两种分层路线

短样本路线应在章节组或局部故事弧处转为自上而下回查；整本路线应继续形成卷级和全书骨架后再向下回查。两条路线必须复用同一梗概提取和事实补全代码。

### FR-05：按需事实补全

第三模块应先由大纲节点生成事实需求，再回原文提取支撑核心事件、人物持续状态、人物关系、世界限制、时间空间和后续生成的必要事实。没有对应需求的内容不得为了提高覆盖率进入事实底座。

### FR-06：唯一叙事图谱

系统应建立实体合并、人物关系、事件因果、时空、人物状态、知识状态和线索生命周期组成的 `narrative_graph.json`。

### FR-07：伏笔生命周期

只有前文设置和后文回应都存在证据时，线索才能标为已验证伏笔。样本之外未知的内容必须保持开放状态。

### FR-08：多重模板提取

系统应保留宏观、事件、场景、人物、节奏和悬念模板。模板先属于作品；只有跨章节和跨作品重复出现并通过反例检查后，才能升级为作者模板。

### FR-09：风格蒸馏

系统应按场景类型量化叙述视角、叙述距离、句段长度、对话/动作/心理/环境比例、信息释放、情绪推进、修辞和负面倾向。

### FR-10：Skill 编译

系统应根据用户输入的作者代号生成独立导出包。公共代码和文档使用“小说作者”等通用称谓，不得写死具体作者。

### FR-11：受控生成

生成每段正文前只读取相关图谱子图、段落任务、场景状态、上一段收束和宏观约束。每章完成后产生图谱补丁，只有正文、状态和因果通过后才能提交。

### FR-12：评测与归因

系统应分别报告提取遗漏、大纲错误、事实不足、图谱错误、检索错误、生成执行错误、模型能力不足和校验器误判，避免通过降低标准掩盖故障。

## 4. 非功能需求

- 模块解耦：模块间只通过版本化 JSON 通信。
- 可恢复：长任务支持分片检查点和安全续跑。
- 可审计：关键结论能追溯到原文证据。
- 可配置：模型、思考模式、章节范围和路线由配置选择。
- 通用性：禁止针对某一部小说硬编码人物、地名、称谓或情节规则。
- 私有性：第一模块、小说语料、密钥和真实运行产物不进入公共 Git。

## 5. 总体验收

正式作者 Skill 至少使用多部作品。短样本只用于模块迭代。重建评测以核心事件覆盖、顺序、因果、人物选择和状态变化为主，不以原文字面相似作为主要指标；同时必须单独评测文章完整度和文风执行。
