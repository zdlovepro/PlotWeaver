# 软件设计规格（SDS）

## 1. 设计结论

系统采用端口式阶段架构：调度器管理执行顺序，公共契约定义文件格式，公共基础设施提供模型、JSON、切分和产物能力，各业务模块只实现自己的阶段。第一模块为本地私有实现。

## 2. 包结构

```text
pipeline/
  cli.py
  orchestrator/
  contracts/
  common/
  modules/module_00_ingestion/
  modules/module_01_local_synopsis_private/
  modules/module_02_hierarchical_outline/
  modules/module_03_fact_hydration/
  modules/module_04_narrative_graph/
  modules/module_05_template_mining/
  modules/module_06_style_distillation/
  modules/module_07_skill_compiler/
  modules/module_08_generation/
  modules/module_09_evaluation/
```

## 3. 阶段接口

每个模块公开一个 `api.py`，统一接受 `StageContext` 并返回 `StageResult`。内部提示词、解析器和修复器不属于公共 API。调度器从配置中的 Python 入口动态加载模块。

```python
def run(context: StageContext) -> StageResult:
    ...
```

`StageContext`至少包含作者、作品、运行 ID、运行配置、输入产物和模型策略。`StageResult`至少包含输出文件、质量报告、是否接受和诊断。

各业务阶段的职责和原文访问权限以 [MODULE_BOUNDARIES.md](MODULE_BOUNDARIES.md)
为实现约束；接口适配不得改变职责归属。

## 4. 第一模块设计

第一模块由以下内部组件组成：

```text
api.py          运行入口
windowing.py    目标窗口和只读前后文
prompts.py      中文提示词及 JSON 正反例
parser.py       中文梗概字段到 ChapterSynopsisBundle 的转换
quality.py      梗概完整度、因果和粒度质量报告
service.py      调用编排和检查点
artifacts.py    标准产物写入
```

局部窗口只理解目标段落，邻接文本仅供消解窗口边界。模型把每个窗口压缩为 0—3 个
主要剧情段，不逐段登记动作、称谓或用途；首窗口同时给出一个 `opening_frame`，末窗口
给出一个 `ending_frame`，中间窗口的对应字段为空。章节合并只读取结构化局部剧情段、
这两个边界句，不再读取原文锚点，并压缩为至多 8 个核心剧情节点和至多 6 个章节
阶段，不重新传入整章原文，也不产出事实、命题或实体。解析器最终以局部边界句覆盖模型
自由生成的首尾状态，防止状态倒退。

第一模块每个局部窗口最多调用三次：剧情段初稿、剧情段语义审校、首/末窗口固定的独立边界微任务，
或中间窗口仅在程序发现明确问题时执行的定向修复；每章固定三次：章纲初稿、结构粒度审校、边界/数量/状态终审。重试只处理传输或
JSON 格式故障，不能替代内容修复。

章级第三次终审不返回完整章纲，只返回四类最小补丁：一句话梗概、按既有 ID 替换的核心节点、
完整未决问题数组、按既有 ID 替换的章节阶段。程序不允许补丁新增、删除或重排节点；未列出的内容保持不变。
程序会把确定性质量问题映射到必须修订的补丁字段，并在应用后重新校验完整章纲。
补丁若遗漏指定字段、违反契约或引入新的硬错误，会被拒绝提交；只有补丁后结果通过质量门才能取代审校前的合格章纲。

首/末窗口的第三次请求只读取最前两段和最后三段，使用带证据 ID 的独立边界对象；默认不再携带
局部剧情段。只有第二阶段存在程序明确定位的内容错误时，同一回复才额外包含独立的剧情段修订数组。
首窗口只允许 `opening_frame` 对应对象，末窗口只允许 `ending_frame` 对应对象，模块内部再补齐公共契约。
这样“剧情段可以为空”的规则不会误清空必须存在的章节边界。

边界微任务若同时发现局部剧情段错误，只返回按 `L1`、`L2` 等稳定 ID 表示的最小修订补丁。
程序把每条错误定位到稳定剧情段 ID，要求补丁 ID 集合与错误目标完全一致；只替换这些剧情段，
未列出的已审校剧情段保持不变。补丁不得新增、删除、重排或修订错误对象之外的剧情段。

审校回复中的“发现的问题”作为审计说明保存，但不自动视为修订后结果仍有错误；只有解析器或
确定性质量门在当前修订稿上仍检测到的问题，才会触发第三次内容修复，避免重复修订破坏合法枚举。

确定性质量门同时覆盖局部剧情段和首尾边界帧，检查阶段提前、全体筛选结果、护送者与被护送者
人数、章末关键追问以及无依据万能悬念。章级结构审校后的错误会作为明确问题交给状态补丁终审。

## 5. 分层大纲设计

第二模块执行可配置的层级归并：

```text
chapter_synopsis -> story_arc -> volume -> book
```

`short_validation`的最高层是`story_arc`；`full_book`的最高层是`book`。达到最高层后，由大纲节点产生事实需求并交给第三模块。模型不得在没有后文的短样本中补写全书走向。

## 6. 事实补全设计

第三模块分两步运行：先把大纲节点转换为带原因和优先级的 `FactRequirement`，再按章节和段落回原文回答这些问题，形成 `HydratedFact`。每条事实必须同时引用需求 ID、大纲节点 ID 和原文证据。第三模块不负责全局实体合并。

## 7. 图谱设计

第四模块维护唯一事实底座。节点包括实体、事件、状态、地点、时间锚点和线索；边包括参与、因果、先后、位置、关系、知晓、状态改变、设置和回应。生成器只能通过检索接口获取当前段落相关子图。

补丁状态为：`proposed -> validated -> committed`或`rejected`。补丁提交前检查正文支持、人物状态、事件因果和跨章连续性。

## 8. 模板与风格设计

模板模块输出作品模板和作者模板两个命名空间。每个模板保存适用条件、步骤、叙事作用、支持样本、覆盖作品、反例和稳定度。风格模块按场景类型输出量化指标、允许范围、文本作用和负面约束。

原作专有名称、世界设定和具体事件不得直接进入作者模板；它们只属于作品图谱或评测基准。

## 9. 可靠性

- 输入产物按内容哈希寻址。
- 阶段产物写入临时文件并通过校验后再标记接受。
- JSON 格式重试与内容修复分开；内容修复必须携带明确问题清单。
- 失败检查点不得冒充正式产物。
- 下游只读取`accepted: true`的产物清单。

## 10. 迁移策略

先固定目录和契约，再完成第一模块；旧下游代码按职责移动但暂不保证全部联通。后续逐模块把内部导入改成公共契约和文件接口。`v2/`作为历史参考保留，不参与新版运行。
