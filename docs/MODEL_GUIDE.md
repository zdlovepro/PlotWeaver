# 模型使用、微调与文风评测说明

本项目中的“模型”不是一件事。推理服务、基础模型、LoRA、SFT、DPO、风格判别器分别解决不同问题；混在一起会导致“模型已经调了，为什么剧情还不对”的误判。

## 1. 先给结论

1. **图谱与标注先于微调。** 如果输入事实不完整或把人物关系、地点状态、伏笔标错，任何 LoRA 都会稳定地学会错误。
2. **本地模型可以用，且适合后续训练。** 当前 Python 流水线通过 OpenAI 兼容接口调用模型；只要本地服务暴露兼容接口，就能先直接替换远程 API。
3. **LoRA 不是基础模型，也不是训练任务。** 它是给基础模型加上的小型可训练适配器；一个基础模型可挂多个不同小说作者的 LoRA。
4. **SFT 教“应该怎么写”，DPO 教“多个都能写时偏好哪一个”。** 应先做 SFT，评测可信后才做 DPO。
5. **风格判别器和写作模型应分离。** 写作模型负责写，判别器负责测它是否接近目标作者而非只是像修仙题材。

## 2. 四种使用层级

| 层级 | 是否训练参数 | 解决什么 | 当前适用性 |
|---|---:|---|---|
| A. 提示词 + 子图推理 | 否 | 结构化标注、事实受控生成、快速迭代 | 立即可用 |
| B. 本地推理服务 | 否 | 降低调用成本、保护本地语料、便于批量候选 | 立即可接入 |
| C. LoRA + SFT | 是 | 将目标作者的场景写法内化为适配器 | 图谱与风格数据稳定后 |
| D. LoRA + DPO | 是 | 让模型偏向事实正确、风格更贴合的候选 | SFT 与评测器稳定后 |

### A. 提示词与约束生成

这是当前系统的基础。模型收到的是“本段事实子图 + 状态 + 风格程序”，而不是原文。优点是立即可控、易定位错误；缺点是模型仍会出现通用 AI 腔，且很难长期稳定遵守精细的文风节奏。

### B. 本地推理服务

本地推理是把已下载的开源基础模型运行在自己的机器或服务器上，通过 HTTP 接口供项目调用；它**不改变模型参数**。常见选择：

| 服务 | 适合场景 | 特点 |
|---|---|---|
| Ollama | 快速试验、单机 | 安装简单，量化模型友好，吞吐较低。 |
| llama.cpp | 显存较小或 CPU/GPU 混合 | GGUF 量化成熟，适合推理，不用于 LoRA 训练。 |
| vLLM | 有 NVIDIA GPU、批量任务 | 并发与吞吐高，适合标注和多候选生成。 |
| SGLang | 多轮、结构化和批处理推理 | 适合复杂推理服务，可按部署环境评估。 |

中文小说建议优先试验中文能力较强的开源指令模型，并固定一个模型作为评测基线。基础模型负责语言能力；项目的事实图谱与风格程序负责可控性。不要在未评测前仅因模型名称或参数量更大就切换模型。

当前项目只需把 `config.yaml` 配置为对应服务的 OpenAI 兼容地址、模型名和密钥/占位密钥，即可把标注、风格分析、生成请求切到本地服务。训练部分另行运行，不应塞进每次小说流水线。

### C. LoRA 与 SFT

**LoRA（Low-Rank Adaptation）**冻结基础模型的大部分权重，只训练少量低秩矩阵。因此保存的是一个小适配器，而不是完整新模型；推理时加载“基础模型 + 某小说作者 LoRA”。它比全量微调更省显存、更便于切换作者。原始论文及实现见 [LoRA](https://arxiv.org/abs/2106.09685) 和 [Hugging Face PEFT](https://github.com/huggingface/peft)。

**SFT（监督微调）**是训练方式：输入一个段落的“去原文化事实/场景/风格程序”，目标输出为该段原文。它教模型在给定同类控制条件时形成目标写法。

训练样本应是：

```json
{
  "input": {
    "paragraph_program": "匿名事件、状态、场景目标与篇幅",
    "local_graph": "仅当前段允许事实",
    "scene_style_program": "本段风格约束"
  },
  "target": "该段原文"
}
```

这里“原文不进入生成器”的规则指**推理/重建时**不能把待重建章节原文作为上下文；在离线训练中，原文作为监督标签是允许且必要的。训练、验证、测试必须按作品或连续章节隔离，不能让同一段原文同时出现在训练和盲测中。

起步建议：先用 7B–14B 级中文基础模型和 QLoRA/LoRA 做小样本实验；它足以验证数据格式与评测方法。显存需求高度依赖模型、量化、序列长度和批量：量化推理通常需求远小于训练；单卡训练前应先做短跑测显存，而不应依据固定数字承诺可行性。

### D. DPO

**DPO（Direct Preference Optimization）**不是让模型背诵原文，而是针对相同输入比较两个候选：

```text
相同段落程序
  chosen：事实完整、文风达标、人工或可信评测认可的文本
  rejected：同一事实下风格偏离、AI 腔、节奏失衡或存在逻辑问题的文本
```

训练目标是让模型更偏向 `chosen`。DPO 不需要单独训练奖励模型，适合在已有 SFT 适配器后做偏好修正；[论文](https://arxiv.org/abs/2305.18290) 与 [TRL 的 DPOTrainer](https://github.com/huggingface/trl)可直接参考。

不要直接把“原文”设为唯一 `chosen`、把任意生成稿设为 `rejected`，然后只依据字面重合度训练。这会奖励复写。正确做法是先通过图谱核验内容，再用场景级风格评分和人工抽检构造偏好对。

## 3. 文风判别器：写作模型之外的第二个模型

写作模型不能可靠地评估自己。建议建立两个评分器并融合：

1. **可解释统计评分器：** 中文字符 n-gram、标点、句长、段长、对话比例、连接方式、词性/句法近似特征。
2. **作者风格嵌入/分类器：** 用目标作者为正样本、多个同题材作者为负样本，尽量剥离题材与角色名影响。

风格表示应做对比学习或至少做对照语料训练；否则“灵气、法宝、筑基”等高频题材词会成为伪风格。关于将内容与作者性分离，可参考 [Contrastive Disentanglement for Authorship Attribution](https://doi.org/10.1145/3589335.3652501)；少样本文风迁移的 [TinyStyler](https://arxiv.org/abs/2406.15586) 和风格引导生成的 [StyleMC](https://arxiv.org/abs/2312.17242)提供了可借鉴的思路。

判别器只用于选择/训练，不把原文段落作为生成上下文。部署时应有“防复写”反向指标：最长公共字符串、字符 n-gram 重合、近重复句和向量近邻均超过阈值时拒绝候选。

## 4. 推荐的本地训练技术栈

| 部分 | 推荐工具 | 用途 |
|---|---|---|
| 基础模型与分词器 | `transformers` | 加载开源中文模型。 |
| LoRA/QLoRA | `peft` + `bitsandbytes` | 训练和保存轻量作者适配器。 |
| SFT/DPO | `trl` | `SFTTrainer`、`DPOTrainer` 与训练日志。 |
| 数据集 | `datasets` | 版本化训练/验证/测试拆分。 |
| 推理服务 | vLLM / SGLang / Ollama | 提供 OpenAI 兼容接口给 V3 流水线。 |
| 风格特征 | 自建中文字符统计 + 中文编码器 | 作者判别、重排和回归评测。 |

安装这些包不应立即写入主流水线依赖。训练应放在独立的 `training/` 子系统，并锁定模型、数据集、随机种子、LoRA 参数和评测结果；训练输出只作为可选 `style_adapter` 被运行时加载。

## 5. 推荐实施顺序

1. 修复标注、关系、空间状态、因果和闭环伏笔，建立可用的留出集。
2. 建立场景风格程序与无训练的多候选重排，得到“有/无风格控制”的可比较基线。
3. 收集多个同题材对照作者语料，训练风格判别器并验证它没有只识别题材词。
4. 构造“段落程序 → 原文段落”的 SFT 数据，先训练小 LoRA，盲测留出作品。
5. 只有当事实校验、风格判别和人工抽检一致时，才用候选对做 DPO。
6. 将通过验收的 LoRA、风格画像、判别器版本一起打包到 `<作者标识>_skill/`。
