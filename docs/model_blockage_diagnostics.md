# 模型相关阻塞诊断规范

正式流程出现卡壳时，先定位失败发生在哪个模型阶段，再判断根因。禁止只根据最终报错或最终 JSON 猜测。

诊断时必须依次读取：

1. 该阶段实际发送的 `.request.txt` 或 `.request.json`；
2. 每次 `.attempt-*.raw.txt` 原始返回；
3. `.attempt-*.meta.json` 中的完成原因、JSON 解析状态和输入输出长度；
   若存在 `.attempt-*.reasoning.txt`，同时读取模型实际推理内容；
4. 阶段结果、程序契约错误与后续审校结果；
5. 错误位置对应的原文、锁定上游内容以及模型实际看见的证据 ID。

报告根因时区分四类：

- 模型内容能力：请求清楚、证据充分、解析正常，但返回语义仍错误；
- 提示词或上下文设计：任务耦合、职责冲突、输入过量、证据不可见或锁定关系不清；
- 程序协议：字段、ID、合并、转义、截断或解析逻辑导致有效内容被拒绝或错误内容被接受；
- 审校能力：生成结果本身与审校结论不一致，包括漏检和误报。

若证据指向模型能力或提示词设计，应提醒用户可以在 `experiments/` 下建立或运行职责单一的模型实验。正式模块不得暗中增加重试来掩盖阻塞；第一模块每个模型调用只执行一次，允许的内容修订也必须是流程中公开的一次性阶段。
